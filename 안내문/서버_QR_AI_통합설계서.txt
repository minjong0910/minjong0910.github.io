## 1. 현재 상태 진단 (v41 실측)

코드를 직접 분석한 결과입니다.

| 항목 | 현재 상태 | 수치 |
|---|---|---|
| 구조 | 단일 HTML, 서버 통신 **전혀 없음** | `fetch()` 호출 0건 |
| 사진 | HTML 안에 base64로 내장 | 위치코드 112개 / 사진 133장 |
| 3D 뷰어 | base64로 통째 내장 | 2.86MB |
| 라이브러리 | THREE.js + JSZip 인라인 | 0.70MB |
| 데이터 저장 | 브라우저 localStorage 6종 | `sugQueue`, `favRooms`, `recentRooms`, `sphDeletedPhotos`, `admFailCount`, `admLockUntil` |
| 화면 | 17개 섹션 | `s1`, `s2`, `scat`, `s3`~`s7`, `sph`, `sset`, `sguide`, `sfav`, `ssug`, `sadmin`, `sphmgr`, `spwgate`, `phsort` |
| 사진 판별 AI | **미탑재** | `SUGAI`, `EMBEDDED_AIVEC` 검색 결과 0건 — 설계서만 존재 |
| 위치 인식 | 없음 (사용자가 출발층 직접 선택) | `startFloor` 변수 |

### 지금 구조가 만드는 4가지 문제

1. **제보가 제보자 폰에만 남는다.** `SUG_QUEUE`는 localStorage에 저장돼서, A가 제보한 사진을 관리자 B가 볼 방법이 없다. 현재 건의함은 사실상 "혼자 쓰는 메모장"이다. — 이게 서버가 필요한 가장 큰 이유
2. **사진 하나 바꾸려면 16.5MB 파일을 통째로 재배포**해야 한다.
3. **관리자 비밀번호가 코드에 그대로 있다.** (`var ADMIN_PW = '2101042';` — F12로 누구나 확인 가능)
4. **사용자가 지금 어디 있는지 앱이 모른다.** 출발점을 매번 손으로 골라야 한다.

> **발표 방어 포인트**: "1번 문제는 아키텍처의 한계이지 버그가 아니며, 서버 도입으로 해결했습니다"라고 말할 수 있으면 중간발표 지적사항을 그대로 성과로 바꿀 수 있습니다.

## 2. 만들 것 — 3개 시스템의 관계

```
                    ┌──────────────────────────┐
                    │   사용자가 QR을 스캔      │
                    └────────────┬─────────────┘
                                 ▼
              ① QR 위치판별 시스템  ← 정확도 100%, 즉시
                                 │
                    현재 위치 확정 (13210 / HALL3L / EV2 …)
                                 │
                                 ▼
                    기존 경로안내 로직에 출발점 자동 입력


              ② 서버 (FastAPI + Firestore)
                 ├─ 위치 검증 · 사진 배포 · 제보 수집
                 ├─ 관리자 인증 (하드코딩 비번 제거)
                 └─ 이용 통계 (발표 자료용)


              ③ 사진 판별 AI
                 ├─ 건의함 제보 자동 분류  ← 주 용도
                 └─ QR이 없거나 훼손된 곳에서 위치 추정 ← 보조
```

**세 시스템의 역할 분담을 명확히 합니다.**

| | QR | AI |
|---|---|---|
| 정확도 | 100% | 80~93% (기존 설계서 실측치) |
| 속도 | 즉시 | 0.1~0.3초 + 업로드 |
| 실패 조건 | 스티커 훼손·미부착 | 유사한 강의실, 조도 변화 |
| 역할 | **주 위치추정** | **보조 + 제보 분류** |

> QR을 1순위로 두고 AI를 백업으로 두는 이 구조가, "왜 SLAM을 안 썼나"에 대한 설계적 답변이 됩니다. 정확도·비용·구현난이도 3축에서 QR이 우월하고, AI는 QR이 못 하는 영역(제보 사진 분류)을 담당합니다.

### 3.2 왜 Cloud Run인가 (Firebase Functions 아님)

Firebase를 쓰기로 했지만, **FastAPI는 Firebase Cloud Functions보다 Cloud Run이 맞습니다.**

| | Cloud Functions | **Cloud Run (권장)** |
|---|---|---|
| FastAPI 그대로 실행 | 래핑 필요 | **Dockerfile로 그대로** |
| AI 모델 탑재 | 배포 크기 제한 빡빡 | **컨테이너에 자유롭게** |
| 콜드스타트 제어 | 어려움 | **min-instances 설정 가능** |
| Firebase Hosting 연결 | 가능 | **가능 (rewrite로 동일)** |

Firebase Hosting의 `rewrites` 설정으로 Cloud Run을 연결하면, 사용자에게는 `https://프로젝트.web.app/api/...` 하나의 도메인으로 보입니다. Firebase 생태계 안에 그대로 있는 셈입니다.

```json
// firebase.json
{
  "hosting": {
    "public": "public",
    "rewrites": [
      { "source": "/api/**", "run": { "serviceId": "b3nav-api", "region": "asia-northeast3" } }
    ]
  }
}
```

> 리전은 **asia-northeast3 (서울)** 로 고정하세요. 발표장에서 응답 지연이 눈에 띄게 줄어듭니다.

### 3.3 비용 — 카드 등록이 필요한가

**결론: Blaze 플랜 등록이 필요하지만, 이 프로젝트 규모에서 실제 청구액은 0원입니다.**

| 서비스 | 무료 한도 | 우리 예상 사용량 | Spark(무료)로 가능? |
|---|---|---|---|
| Firestore | 읽기 5만/일, 쓰기 2만/일, 저장 1GiB | 읽기 200/일 미만 | ✅ 가능 |
| Firebase Hosting | 10GB 저장, 360MB/일 전송 | 1MB 앱 × 수십 회 | ✅ 가능 |
| Cloud Run | 월 200만 요청, 180,000 vCPU-초 | 수천 요청 | ❌ 결제 계정 필요 |
| Cloud Storage | Blaze 내 무료 한도 | 사진 133장 ≈ 20MB | ❌ 2024년 9월부터 Blaze 필수 |

**대응 방안 2가지 — 팀 사정에 맞게 고르세요.**

**A안 · Blaze 등록 (권장)**
신규 가입 시 $300 크레딧이 제공되고, Cloud Run·Storage 모두 무료 한도 안에서 돌아갑니다.
반드시 **예산 알림을 1,000원으로 설정**해 두세요 (GCP 콘솔 → 결제 → 예산 및 알림). 사고 방지용입니다.

**B안 · 완전 무료 (카드 없이)**
- 데이터: Firestore만 사용 (Spark 무료)
- 사진: Cloud Storage 대신 **Firestore 문서에 압축 base64로 저장** (문서당 1MB 제한 → 압축 사진 150KB면 충분, 133장 × 150KB ≈ 20MB로 1GiB 한도의 2%)
- FastAPI: 학교 실습실 PC 또는 팀원 노트북에서 실행 + **Cloudflare Tunnel**로 외부 공개 (무료, 카드 불필요)

> B안은 발표 당일 노트북이 켜져 있어야 한다는 리스크가 있습니다. **발표 안정성을 생각하면 A안**, 카드 등록이 곤란하면 B안입니다. 어느 쪽이든 코드는 동일하고 배포 설정만 다릅니다.

## 4. ① QR 위치판별 시스템

### 4.1 QR에 무엇을 담을 것인가

**결정: 서명이 포함된 짧은 URL을 담습니다.**

```
https://gunsan-b3nav.web.app/q/13210.a7f3c1
                              ─┬───  ─┬────
                               │      └─ HMAC-SHA256 앞 6자리 (위조 방지)
                               └─ 위치 코드
```

**왜 이 형식인가**

| 후보 | 장점 | 단점 | 채택 |
|---|---|---|---|
| 순수 텍스트 `B3NAV:13210` | 오프라인 동작 | 카메라 앱으로 찍으면 아무 일도 안 일어남 | ✗ |
| 서명 없는 URL | 단순 | 누구나 가짜 QR 제작 가능 | ✗ |
| **서명 포함 URL** | 카메라 앱으로 찍어도 앱이 열림, 위조 방지 | 서버 필요 (오프라인 폴백으로 해결) | **✓** |

**핵심 이점**: 사용자가 우리 앱을 안 켜고 **폰 기본 카메라로 QR을 찍어도** 앱이 해당 위치에서 바로 열립니다. 앱 설치·실행이라는 진입장벽이 사라집니다.

**오프라인 폴백**: URL 경로에 위치 코드가 평문으로 들어있으므로, 서버가 죽어도 앱은 코드를 파싱해 위치를 설정할 수 있습니다. 서명 검증만 건너뜁니다.

### 4.2 QR 부착 위치 (112개소)

| 구분 | 개수 | 부착 위치 | 우선순위 |
|---|---|---|---|
| 건물 출입구 (BLD) | 8 | 정문·후문·동문·서문의 안팎 | **1순위** |
| 엘리베이터 (EV1~EV5) | 5 | 각 층 EV 앞 벽면 | **1순위** |
| 복도 (HALL1L~5R) | 10 | 각 층 좌/우 복도 중앙 | **1순위** |
| 지하 (B1) | 1 | 계단 하단 | 2순위 |
| 강의실·연구실 | 92 | 출입문 옆 | 3순위 |
| 특수 (13121-A/B, KTC) | 3 | 해당 위치 | 3순위 |

> **발표 준비 팁**: 92개 강의실까지 다 붙일 필요 없습니다. **1순위 23개소만 실제 부착**하고 시연하면 충분합니다. 나머지는 "생성·출력까지 완료, 부착만 남음"으로 발표하면 됩니다.

### 4.3 스티커 생성 자동화

`scripts/generate_qr_sheets.py`가 A4 시트 PDF를 만듭니다.

- 한 장에 3×4 = 12개 배치
- 각 QR 아래에 **사람이 읽을 수 있는 위치명** 병기 (예: `3층 좌측 복도 / HALL3L`)
- 부착 실수 방지를 위해 구분별 테두리 색상 적용 (출입구=시안, EV=마젠타, 복도=보라, 호실=회색 — 앱의 네온 팔레트와 동일)
- 여백에 절취선, 코팅 후 부착 권장

### 4.4 앱 쪽 스캔 구현

```javascript
/* QR 스캔 — 2단계 폴백 구조 */
async function qrScan() {
  // 1순위: BarcodeDetector (Android Chrome 네이티브, 빠름·가벼움)
  if ('BarcodeDetector' in window) {
    const detector = new BarcodeDetector({ formats: ['qr_code'] });
    // getUserMedia로 후면 카메라 스트림 → detect() 루프
  }
  // 2순위: jsQR (iOS Safari 등 미지원 브라우저, 약 40KB)
}
```

| 브라우저 | BarcodeDetector | 폴백 |
|---|---|---|
| Android Chrome | ✅ 지원 | — |
| iOS Safari 17+ | ❌ 미지원 | jsQR |
| 데스크톱 Chrome | ✅ 지원 | — |

**카메라 권한은 HTTPS에서만 허용됩니다.** Firebase Hosting은 기본 HTTPS라 문제없지만, 로컬 테스트는 `localhost` 또는 터널 URL을 쓰세요.

### 4.5 스캔 후 동작

```
QR 스캔 성공
   │
   ├─ 서버 응답 OK  → 위치 확정 + 최신 사진 갱신 + 통계 기록
   ├─ 서버 응답 없음 → URL에서 코드만 파싱해 위치 확정 (오프라인 모드 배지 표시)
   └─ 서명 불일치   → "인증되지 않은 QR입니다" 경고 후 수동 선택 유도
   │
   ▼
startFloor / 현재위치 자동 설정 → 목적지만 고르면 바로 경로 안내
```

## 5. ③ 사진 판별 AI (서버 이전)

기존 설계서 `건의함_사진판별AI_설계.md`의 파이프라인을 **그대로 계승**하되, 2단계를 서버로 옮깁니다.

### 5.1 무엇을 어디서 돌릴 것인가

| 단계 | 위치 | 이유 |
|---|---|---|
| 1단계 품질검사 (흔들림·밝기·해상도) | **클라이언트** | 순수 JS, 오프라인 동작, 불량 사진을 업로드 전에 걸러 트래픽 절약 |
| 2단계 위치 판별 (임베딩·유사도) | **서버로 이전** | 모델 14MB 다운로드 불필요, 모델 교체 자유, 벡터 재계산 자동화 |

### 5.2 서버 이전으로 새로 가능해지는 것

기존 클라이언트 방식에서는 불가능했던 3가지입니다. **발표에서 "서버를 왜 도입했나"의 직접적 답변이 됩니다.**

1. **교차 검증 자동 반영** — 같은 위치에 서로 다른 3명 이상이 유사한 변화를 제보하면 관리자 승인 없이 자동 반영 (기존 설계서 9장에서 "자연스러운 다음 단계"로 언급된 항목)
2. **모델 자유도** — MobileNet(1280차원) → CLIP/DINOv2로 교체해도 사용자는 재다운로드 불필요. 14MB 제약이 사라짐
3. **벡터 자동 재계산** — 사진을 추가하면 서버가 즉시 임베딩을 갱신. `SUGAI.export()` 후 HTML에 붙여넣는 수동 작업이 없어짐

### 5.3 모델 선정

| 모델 | 크기 | 콜드스타트 | 정확도 | 채택 |
|---|---|---|---|---|
| **MobileNetV3-Small (ONNX)** | 15MB | 1~2초 | 기존 실측 80~93% | **✓ 1차** |
| CLIP ViT-B/32 | 350MB | 10초+ | 더 높음 | 여유 있으면 2차 |

ONNX Runtime을 쓰면 PyTorch 전체(2GB+)를 컨테이너에 넣지 않아도 되어 이미지 크기와 콜드스타트가 크게 줄어듭니다.

### 5.4 임계값 (기존 설계서 계승)

```python
TH_RELEVANT = 0.42   # 미만 → 건물과 무관한 사진, 자동 반려
TH_MATCH    = 0.60   # 초과 → 위치 자동 확정
TH_SAME     = 0.965  # 초과 → 기존 사진과 거의 동일, 안내 후 접수
```

실측 근거는 기존 설계서 4장의 표를 그대로 인용하면 됩니다.

### 5.5 QR과 AI의 협업

QR을 스캔한 상태에서 제보하면 **위치가 이미 확정**되어 있으므로, AI는 "이 사진이 정말 그 위치가 맞는지" 검증만 하면 됩니다. 판별 문제가 분류(112지선다)에서 확인(예/아니오)으로 바뀌어 정확도가 크게 올라갑니다.

```
QR 스캔 후 제보  → AI는 검증만  → 신뢰도 높음 → 자동 반영 후보
QR 없이 제보     → AI가 분류    → 신뢰도 보통 → 관리자 검토 필수
```

### 6.2 사진

| 메서드 | 경로 | 설명 | 인증 |
|---|---|---|---|
| GET | `/photos/manifest` | 전체 사진 목록 + 버전 해시 (앱 시작 시 1회) | 없음 |
| GET | `/photos/{code}` | 특정 위치 사진 목록 | 없음 |

> `manifest`에 **버전 해시**를 넣는 이유: 앱이 해시만 비교해 변경이 없으면 사진을 다시 안 받습니다. Firestore 읽기 횟수와 데이터 전송량이 크게 줄어듭니다.

| POST | `/sug/{id}/reject` | 거절 | 관리자 |

    "confidence": 0.87,
    "runner_up": { "code": "13212", "confidence": 0.41 },

### 6.4 관리자 인증

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/auth/login` | 비밀번호 → JWT 발급 (24시간 유효) |
| POST | `/auth/refresh` | 토큰 갱신 |

**`var ADMIN_PW = '2101042'`를 코드에서 제거합니다.** 비밀번호는 서버에 bcrypt 해시로만 저장하고, 클라이언트는 토큰만 갖습니다. 기존의 로고 5번 탭 + 5회 실패 30초 잠금 UX는 그대로 유지합니다.

| 메서드 | 경로 | 설명 |

### 읽기 횟수 최적화

Firestore 무료 한도는 일 5만 읽기입니다. 넉넉하지만 아래 3가지를 지키면 사실상 소진되지 않습니다.

1. `locations` 112개 문서를 **하나의 `manifest` 문서로 합쳐** 앱 시작 시 1회만 읽기 (112회 → 1회)
2. 클라이언트에 **버전 해시 캐싱** — 변경 없으면 재조회 안 함
3. 통계는 개별 문서 대신 **일자별 문서에 누적 업데이트**

## 8. 기존 HTML 통합 지점

v41 코드를 직접 확인한 결과, 아래 지점만 손대면 됩니다. **기존 3D 뷰어·경로안내 로직은 건드리지 않습니다.**

| 대상 | 위치 (v41 기준) | 변경 내용 |
|---|---|---|
| 화면 목록 | `var SCREENS = [...]` (약 1534행) | `'sqr'` 추가 — QR 스캔 화면 |
| QR 스캔 화면 | `#ssug` 섹션 근처 | 신규 `<section id="sqr">` + 카메라 프리뷰 |
| 첫 화면 | `#s1` | "QR 스캔" 큰 버튼 추가 (네온 시안 계열) |
| 사진 로딩 | `EMBEDDED_PHOTOS` 파싱부 (644행) | base64 내장 → `/photos/manifest` fetch로 교체, 실패 시 내장 데이터 폴백 |
| 제보 제출 | `sugSubmit()` (1808행) | localStorage push → `POST /sug/submit` |
| 관리자 목록 | `sugAdminRender()` (1869행) | localStorage 조회 → `GET /sug/pending` |
| 제보 승인 | `sugApprove()` (1904행) | 로컬 배열 조작 → `POST /sug/{id}/approve` |
| 제보 거절 | `sugReject()` (1929행) | 동일 |
| 관리자 비번 | `var ADMIN_PW = '2101042'` | **삭제** → `POST /auth/login` + JWT |
| 출발 위치 | `var startFloor = 1` | QR 스캔 결과로 자동 설정 |
| 3D 뷰어 | `B3D_SRC` (643행, 2.86MB) | 외부 파일로 분리, 필요 시 로드 |

### 앱 용량 변화

| | 현재 | 통합 후 |
|---|---|---|
| HTML | 16.5MB | **약 0.9MB** |
| 3D 뷰어 | 내장 2.86MB | 지연 로드 |
| 사진 133장 | 내장 약 12MB | 서버에서 필요 시 |
| 첫 로딩 (LTE) | 20~40초 | **2~3초** |

> **이것만으로도 발표 성과가 됩니다.** "첫 로딩 시간 90% 단축"은 측정 가능하고 직관적인 지표입니다.

### 오프라인 폴백 원칙

서버가 죽어도 앱이 죽으면 안 됩니다. 3단계로 방어합니다.

1. Service Worker로 마지막 응답 캐시
2. 캐시도 없으면 HTML에 남겨둔 **최소 내장 데이터**(1순위 23개 위치 사진)로 동작
3. QR은 URL에서 코드를 직접 파싱 — 서버 없이도 위치 확정 가능

## 11. 예상 질문 대응

**Q. SLAM을 쓰지 않은 이유는?**
Visual SLAM은 실시간 카메라 추적이 필요해 웹 클라이언트에서 성능·배터리 제약이 큽니다. 실내 길안내는 매 프레임 위치 추적보다 **출발점 확정**이 본질이라 판단해, QR 기반 절대위치 확정을 1순위, 이미지 임베딩 기반 추정을 보조로 설계했습니다. 정확도 100%, 구현 비용 1/10입니다.

**Q. QR 스티커가 훼손되면?**
3단계 폴백이 있습니다 — ① 인접 위치 QR ② AI 사진 판별 ③ 기존 수동 선택. 또한 스캔 실패가 서버에 기록되어 훼손 지점을 관리자가 파악할 수 있습니다.

**Q. 서버 비용은?**
Firestore·Hosting은 무료 한도 안이고, Cloud Run도 월 200만 요청까지 무료입니다. 예산 알림을 설정해 두었습니다.

**Q. 개인정보는?**
제보 사진은 건물 시설물만 촬영하도록 안내하고, 위치 통계는 익명 세션 단위로만 집계합니다. 로그인 기능이 없어 개인 식별 정보를 수집하지 않습니다.

**Q. AI 정확도가 80~93%면 낮지 않나?**
AI는 최종 결정권자가 아니라 관리자의 입력을 미리 채워주는 보조입니다. 승인은 사람이 합니다. 또 QR 스캔 후 제보하면 문제가 112지선다 분류에서 예/아니오 확인으로 바뀌어 정확도가 크게 올라갑니다.
