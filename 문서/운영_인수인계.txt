3. 출입문 QR · 주소는 바꾸면 안 된다 (I-3)
────────────────────────────────────────────────────────────────

  붙여 둔 QR 4장과 NFC 스티커는 https://minjong0910.github.io/?gate=… 를 연다.
  그래서 아래를 하면 붙여 둔 것이 모두 엉뚱한 곳을 열거나 「찾을 수 없음」이 된다.
    ✗ GitHub 계정 이름 바꾸기 · 저장소 이름 바꾸기 · 저장소 지우기 · 다른 계정 · 조직으로 옮기기
    ✗ 저장소 설정 → Pages 끄기

  주소를 꼭 바꿔야 할 때
    1. site/js/app/qrnav.js 의 SITE_URL 을 새 주소로
    2. pwsh -File 도구\QR_만들기.ps1  → QR인쇄\ 에 새 그림 4장 + A4 인쇄본 (앱이 쓰는 QR 읽기로 다시 읽어 맞을 때만 저장)
    3. 검사.ps1 — 「출입문 QR 주소 = 이 저장소의 사이트」 검사가 새 주소를 확인한다
    4. 배포한 뒤 새 QR 을 인쇄해 붙이고, NFC 스티커도 새 주소로 다시 쓴다
    5. 옛 주소에서 새 주소로 넘겨주는 페이지를 한동안 남겨 둔다(가능하면)
  (선택) 학교 · 개인 짧은 도메인을 두고 그 도메인이 사이트를 가리키게 하면, 저장소가 바뀌어도 도메인 설정만 고치면 된다.

  정기 확인 — 학기 시작마다
    □ 붙여 둔 QR 4장을 휴대폰 기본 카메라로 찍어 앱이 「○문에 계신가요?」로 열리는지
    □ NFC 스티커도 같은 확인
    □ 떨어지거나 훼손된 것은 QR인쇄\ 의 PDF 로 다시 인쇄


4. 자주 하는 운영 일 (runbook · I-5)
────────────────────────────────────────────────────────────────

  4-1. 건의함 처리 — 수시로, 적어도 한 달에 한 번
    · 앱 설정 → 관리자 로그인 → 사진 등록 → 건의함 검토
    · 승인 : 층 → 장소를 고르고 초록 줄을 확인한 뒤 승인. 그 자리 대표 사진이 모든 사람에게 바뀐다(서버 photos).
    · 거절할 사진 : 사람 얼굴 · 다른 사람의 화면 · 이름표 · 서류가 알아볼 수 있게 찍힌 사진, 3호관이 아닌 사진
      (AI 가 「🚫 건물 사진이 아닌 것 같음」으로 표시하기도 한다), 「⚠ 사진 형식이 맞지 않는 제보」.
    · AI 의 장소 짐작은 참고만 — 확정은 사람이 한다(정확한 자리 55.6%).
    · 이 화면을 열 때 지우는 일을 한다 : 거절한 제보는 바로, 확인 못 한 제보는 30일 뒤, 승인한 제보의 원본은 30일 뒤
      (안내 사진은 photos 에 그대로). 그래서 관리자가 한 달에 한 번은 이 화면을 열어야 개인정보 처리방침이 지켜진다.
    · 관리자가 한 일은 서버 adminlog 에 남는다(승인 · 거절 · 삭제 · 사진 올리기 · 숨기기 · 자동 정리).

  4-2. AI 자료집(site/data/ailib.js) 갱신 — 승인 사진이 쌓였을 때 (예 : 학기마다)
    승인한 사진은 화면과 「모든 기기의 AI」에 바로 반영된다(서버 photos → 앱이 받아 배운다).
    그런데 서버가 없을 때(인터넷이 끊김 · 서버 한도 초과)에도 AI 가 알게 하려면 자료집 파일에 넣어 둔다.
      1. 관리자 PC 에서 앱 → 설정 → 사진 등록 → 🤖 AI 사진 파악 자료집
      2. 「📥 자료집 파일(ailib.js) 내려받기」
      3. 저장소의 site/data/ailib.js 를 그 파일로 바꾼다
      4. pwsh -File 도구\오프라인목록.ps1 → 검사_실행.bat → commit · push
      5. Actions 초록 확인 → 앱을 새로 열어 건의함에 같은 자리 사진을 넣어 보고 맞히는지 본다
    ※ 사용자가 「어디에서 찍으셨나요?」에서 고른 답은 관리자가 승인한 뒤에만 AI 가 배운다(2026-11-10 부터).

  4-3. 사진 자료 묶음(zip)으로 앱 파일에 사진 넣기 — 서버 없이도 보이게 하고 싶을 때
      1. 설정 → 사진 등록 → 사진 · ZIP 을 끌어다 놓고 위치를 맞춘 뒤 넣기
      2. 「사진 자료 묶음(zip) 내려받기」 (내려받기 전에 새로고침 · 창 닫기를 하면 브라우저가 한 번 묻는다)
      3. 압축을 저장소 site/ 에 그대로 풀기(data/photos.js · data/photos/…)
      4. pwsh -File 도구\오프라인목록.ps1 → 검사_실행.bat → commit · push

  4-4. 서버 규칙 게시 — 서버/firestore.rules 를 고쳤을 때 (자동으로 게시되지 않는다)
      1. 서버/규칙_붙여넣기용.txt 가 firestore.rules 와 같은지 — 검사.ps1 이 확인한다(다르면 실패)
      2. Firebase 콘솔 → Firestore Database → 규칙 → 서버/규칙_붙여넣기용.txt 내용을 통째로 붙여 넣고 [게시]
      3. 같은 화면 [규칙 플레이그라운드] 로 확인 — 익명 제보 허용 · 관리자 읽기 · 그 밖 거부 (서버/보안_설정_안내.txt)
      4. 실제 앱으로 제보 1건이 접수되는지, 관리자 화면에 보이는지
      5. 서버/firestore.rules 머리말 「마지막으로 콘솔에 게시한 날」을 고치고 사본도 같게 → commit
    ⚠ 2026-11-10 판(사진 모양 검사 · adminlog · 승인 사진 모양 검사)은 게시해야 적용된다. 게시 전에는 관리자 작업 기록(adminlog)이
      서버에서 거부된다(앱은 계속 동작하고, 문제 기록에 「서버 오류 · 관리자 작업 기록」으로 남는다).

  4-5. 발표가 끝나면 — live 규칙 닫기 (B-7)
      발표장 「지금 켜 둔 사람」(site/live/)을 위해 로그인 없이 쓰는 칸(live · here)을 열어 두었다.
      1. 서버/firestore.rules 의 「match /live/{ev}」 블록 전체를 지운다(또는 allow create, update 를 false 로)
      2. 사본 맞추기 → 4-4 대로 게시 → commit
      site/live/ 페이지는 그대로 두어도 된다(쓰기가 막혀 숫자가 안 오를 뿐이다).

  4-6. 배포가 정말 됐는지
      · Actions 탭 : 검사 · 서버 규칙 시험 · 사이트 바꾸기 · 배포 뒤 사이트 확인 — 모두 초록
      · https://minjong0910.github.io/sw.js 의 VERSION = 저장소 site/sw.js 의 VERSION
      · 시연 전날부터는 배포를 멈춘다(사례 5). 발표용 안정판에는 태그(v171 …)가 있다 — 되돌리기는 설계_배포_복구 5절.

  4-7. 사용자가 「안 된다」고 할 때
      · 앱 설정 → 「문제 기록」 줄을 눌러 복사해 받는다(앱 판 · 오류 · 기기 · 인터넷 · 서비스 워커 · 서버 오류 코드).
      · 옛 화면이 보인다 → 앱을 완전히 닫았다 다시 열기. 그래도면 4-6 으로 사이트 판 확인.
      · 제보가 안 올라간다 → 문제 기록의 「서버 오류」 줄(permission-denied = 규칙, resource-exhausted = 한도, unavailable = 인터넷).

  4-8. 백업 — 큰 수정 전 · 학기 시작 전 · 발표 전날
      pwsh -File 도구\서버_백업.ps1  →  pwsh -File 도구\서버_백업.ps1 -Check  →  생성물\백업\ 을 다른 곳에 옮겨 둔다.
      (설계_배포_복구 7절)

    읽기 하루 50,000번 · 쓰기 하루 20,000번 · 저장 1GiB · 내보내는 데이터 한 달 10GiB
    → 다시 여는 폰 기준 하루 약 6,000번 열기, 처음 여는 폰 기준 한 달 약 4,600대까지.
    승인 사진이 늘면 「처음 여는 폰」의 양이 사진 수에 비례해 는다 — 사진이 30장을 넘으면 다시 계산한다.

  한도를 넘으면
    · Spark : 그날(태평양 시간 자정까지) 서버 요청이 실패한다. 앱의 길안내 · 기본 사진(앱 파일 site/data/photos/)은 그대로 열린다.
      승인 사진은 폰에 저장해 둔 것만 보이고, 건의함 제보는 폰에 남았다가 나중에 다시 보낸다.
    · Blaze : 요금이 나온다 → 아래 예산 알림을 꼭 켠다.

  확인 · 알림 설정 (사람이 콘솔에서)
    □ Firebase 콘솔 → Firestore Database → 사용량 탭 — 읽기 · 쓰기 그래프를 발표 · 오리엔테이션 뒤에 본다
    □ (Blaze 일 때) Google Cloud 콘솔 → 결제 → 예산 및 알림 → 예산(예 : 월 1,000원)을 만들고 50% · 90% · 100% 알림 메일
    □ (Spark 일 때) 요금은 나오지 않는다 — 사용량 탭을 행사 뒤에 확인하는 것으로 충분하다


6. 막지 못한 것 — 하루 3번 우회 (B-4)
────────────────────────────────────────────────────────────────

  하루 3번은 익명 로그인 UID 기준이다. 앱 데이터를 지우거나 시크릿 창을 열면 새 UID 가 생겨 다시 3번을 올릴 수 있다.
  승인 전 제보는 아무에게도 보이지 않으므로 피해는 서버 저장 용량 · 관리자 목록이 붐비는 정도다(30일 뒤 지워진다).
  지금은 「알려진 한계」로 두고(README), 실제로 붐비면 Firebase App Check 를 켠다 :

    1. Firebase 콘솔 → App Check → 웹 앱 등록 → reCAPTCHA Enterprise(또는 v3) 사이트 키 만들기
    2. 앱에 App Check 를 넣는다 — sugdb.js 가 Firebase 를 부르는 곳에 firebase-app-check-compat.js 를 더하고 activate(사이트 키)
       ⚠ 승인 사진 · 방 정보는 SDK 가 아니라 REST(fetch)로 읽는다(sugdb.js restPhotos · 방 정보) — 그 요청에도
         App Check 토큰(X-Firebase-AppCheck 머리글)을 붙여야 한다. 안 그러면 「적용」 순간 모든 사람의 승인 사진이 안 보인다.
    3. 배포 → 콘솔 App Check 에서 Firestore 를 「모니터링」 상태로 1~2주 — 확인된 요청 비율을 본다
       (이미 설치된 폰은 앱을 다시 열어야 새 판이 된다. 옛 판이 남아 있는 동안은 토큰 없는 요청이 섞인다)
    4. 확인되지 않은 요청이 거의 없을 때 「적용(Enforce)」
    5. 발표장 live 는 로그인 없이 쓰므로 App Check 를 적용하면 같이 막힌다 — 4-5 로 먼저 닫는다
