# 공대 3호관 실내 길안내

군산대학교 공과대학 3호관(지하 1층 ~ 5층)의 실내 길안내 웹앱입니다.
강의실 번호·교수님 성함·학과 사무실로 목적지를 찾으면, 3D 건물 모형과 실제 사진으로
엘리베이터에서 내려 어느 쪽으로 몇 번째 방인지까지 안내합니다.

- 졸업작품 · 김민종 · 손의윤 · 문성일
- 주소 : https://minjong0910.github.io/ — 폰 브라우저에서 바로 동작하고, **설정 → 앱 다운로드**로 홈 화면에 앱으로 설치할 수 있습니다.
  처음 열 때 약 18MB 를 폰에 저장해 두어 **인터넷 없이도 열립니다** (AI 사진 판별과 건의함만 인터넷이 필요합니다).
- 출발 위치는 출입문의 **QR**(정문·후문·동문·서문)이나 직접 고른 층으로 정합니다.
  QR 은 앱 주소라서 휴대폰 기본 카메라로 찍으면 앱이 열리고 "○문에 계신가요?" 확인 화면이 뜹니다.
  QR 로 들어오든 위 주소로 들어오든 앱은 같습니다 — 동의 화면 · 쉬운 사용모드 · 이어 하기 · 「엘리베이터 / 중앙계단」 고르는 창 모두.
- **발표 · 시연용 주소** : https://minjong0910.github.io/?consent — 처음 동의 화면은 휴대폰(브라우저)마다 **한 번만** 뜹니다.
  이미 동의한 기기에서 동의 화면부터 다시 보여 주려면 이 주소로 엽니다(동의 기록은 그대로, 화면만 한 번 더).
- **건의함** : 앱 사진이 실제와 다르면 사용자가 사진을 올리고, AI 가 어디인지 *짐작*해 두면
  **관리자가 확인해 승인**합니다. AI 가 스스로 확정하지 않습니다(아래 「정확도」).

## 빠른 시작

```
미리보기_실행.bat        미리보기 서버를 켠다 → http://localhost:8080 (앱이 열린다)
pwsh -File 도구\오프라인목록.ps1   site/ 를 고쳤으면 — 폰에 저장되는 파일 목록(sw.js)을 새로 쓴다
검사_실행.bat            고친 뒤 올리기 전에 — 파일 검사 + 브라우저 검사 (약 1분)
pwsh -File 검사.ps1 -Full   + 1인칭 로드뷰 9가지를 끝까지 재생 (약 4분 더)
```

앱은 **빌드 단계가 없습니다.** `site/` 폴더가 곧 배포되는 앱이고, 거기 있는 파일을 직접 고칩니다.
필요한 것 : Windows · PowerShell 7(`pwsh`) · Microsoft Edge (검사가 Edge 헤드리스를 쓴다). Node·Python 은 필요 없습니다
(서버 규칙 시험만 GitHub 자동 검사에서 Node 로 돕니다 — 아래 「검사」).

## 구조

모든 코드는 브라우저에서 돌아갑니다. 서버는 Firebase(Firestore — 제보·승인 사진·방 정보, Authentication — 익명 · 관리자)뿐이고,
서버 쪽 코드는 없습니다. 권한과 입력 검사는 **Firestore 보안 규칙**이 맡습니다.

`site/index.html` 이 부르는 순서가 곧 실행 순서입니다. 앱 코드는 원래 한 파일(1만 6천 줄)이던 것을

(`검사.ps1` 이 이름이 겹치지 않는지 확인합니다). 새로 짠 부분은 모듈 객체로 묶었습니다 — `SUGAI`(AI), `SUGDB`(서버), `QRNAV`(QR), `NAVGRAPH`(길찾기), `PWA`(설치·오프라인).

## 앱 설치 · 인터넷 없이 열기 · 출입문 QR

- **설치는 사용자가 원할 때만** — 앱은 설치를 조르지 않습니다. 첫 화면에 노란 글씨로 "앱을 다운로드 하시려면 설정에 들어가주세요"만
  보여 주고(누르면 설정), 안드로이드 크롬이 스스로 띄우는 설치 알림도 막습니다(`beforeinstallprompt` 를 받아 둠).
- **설정 → 앱 다운로드** (`PWA.install()`) — 기기마다 다른 안내 :
  안드로이드 크롬·삼성 인터넷은 버튼 한 번에 브라우저 설치 창 · 아이폰·아이패드는 그림 3단계(공유 → 홈 화면에 추가 → 추가, 아이콘·이름과 함께) ·
  카카오톡·인스타그램 같은 앱 안 브라우저는 "크롬/사파리로 열기" · 설치 신호가 아직 없는 안드로이드·PC 는 브라우저 메뉴 안내.
- **인터넷 없이 열기** (`site/sw.js`) — 처음 열 때 `site/` 의 파일 273개(18MB)를 저장하고, 다음부터는 저장한 것으로 엽니다.
  AI 사진 판별 자료(`data/aivec.js`·`ailib.js`)와 AI 라이브러리(`lib/`)는 **저장하지 않습니다** — 끊겨 있으면 건의함이
  "인터넷이 없어 AI 사진 판별은 쉬어요 — 제보는 그대로 되고, 사람이 확인해요"라고 말하고, 다시 연결되면 다시 받습니다.
  파일마다 지문(SHA-256)을 적어 두어, 받은 파일이 목록과 다르면 다시 받고, 새 판이 나오면 바뀐 파일만 받습니다.
  **`site/` 를 고치면 `pwsh -File 도구\오프라인목록.ps1`** 로 목록을 새로 써야 합니다 (안 하면 `검사.ps1` 이 실패로 알려 줍니다).
  미리보기 서버(localhost)에서는 꺼 둡니다 — 고친 파일이 바로 보여야 하니까요 (`?sw=1` 을 붙이면 켜짐).
- **승인 사진** — 관리자가 승인한 사진은 서버(`photos`)에서 받는데, 목록(장소·번호·시각)만 먼저 받고
  **사진 본문은 바뀐 것만** 받아 폰에 따로 저장합니다(`b3srv-photos`). 예전에는 앱을 열 때마다 사진째 통째로 받았습니다(5장에 1.4MB → 이제 두 번째부터 약 4KB).
- **앱을 켜면 늘 최신 판** (2026-09-25) — 앱을 깔면 저장해 둔 사본으로 열리므로, 그냥 두면 고쳐 올려도 옛 화면이 보입니다.
  그래서 두 가지를 합쳐 뒀습니다 :
  ① `sw.js` 는 **첫 화면에 필요한 것(약 700KB)만 먼저 받고 곧바로 넘겨받습니다** — 재 보니 **0.4초**.
     나머지(사진·3D)는 그다음에 배경에서 채웁니다. 예전에는 전부 받을 때까지 기다려서,
     그동안 사용자는 계속 옛 화면을 보고 있었습니다.
  ② `pwa.js` 는 새 판이 넘겨받으면 화면을 **한 번만** 새로 고칩니다. 단 **첫 화면일 때만** —
     길안내 중이거나 카메라(QR)를 켜는 중이면 미뤄 뒀다가, 첫 화면으로 돌아오거나 앱을 다시 열 때 적용합니다.
     처음 설치될 때는 새로 고치지 않습니다(괜히 한 번 깜빡임).
  ③ 그 새로 고침이 **눈에 안 보이게** 합니다 — `pwa.js` 가 `sessionStorage`에 `b3nav_quiet` 표시를 남기고,
     `boot.js` 가 그 표시를 보면 켜는 화면(부팅 연출)을 통째로 건너뜁니다. 사용자 눈에는 앱이 한 번만 켜집니다.
  **사용자가 눌러야 하는 것은 없습니다.** 앱을 열면 알아서 최신 판이 됩니다.
  ※ 옛 판을 지우는 것은 **새 판을 다 옮겨 담은 뒤**에 합니다. 먼저 지우면 '안 바뀐 파일 옮겨 담기'를 못 해
     전부 다시 받게 됩니다.
- **출입문 QR** = `https://minjong0910.github.io/?gate=MAIN` (정문 · `BACK` 후문 · `EAST` 동문 · `WEST` 서문).
  기본 카메라로 찍으면 앱이 열리고 `pwa.js` 가 `?gate=` 를 떼어 두었다가 `QRNAV.fromUrl()` 이 확인 화면을 띄웁니다.
  앱 안 스캐너로 찍으면 주소를 열지 않고 글자만 읽습니다. 예전 인쇄본(`B3NAV1:BLD:MAIN`)도 읽습니다.
  인쇄 그림은 `pwsh -File 도구\QR_만들기.ps1` → `QR인쇄/` — 이 PC 에 QR 프로그램이 없어 `도구/QR_encode.js` 로 직접 만들고,
  앱이 쓰는 QR 읽기(jsQR)로 다시 읽어 맞을 때만 저장합니다.
  **QR 은 이 주소에 묶여 있습니다** — GitHub 계정 이름·저장소 이름을 바꾸면 붙여 둔 QR 이 모두 엉뚱한 곳을 엽니다.
  주소를 바꿔야 할 때의 순서는 [`문서/운영_인수인계.txt`](문서/운영_인수인계.txt) 3절.

## 화면 크기 (기기마다 같은 비율로)

설계 기준은 **390 × 790** 이고, `app.css` 의 크기는 **거의 다 `rem`** 입니다. `1rem` = `html` 의 글자 크기 한 값뿐이라,
그 한 줄만 바꾸면 화면 전체가 같은 비율로 커지고 작아집니다.

- 데스크톱(폰 액자 상태) : `html{font-size:16px}` — 설계한 그대로 보입니다(안전망 그림이 흔들리지 않게).
- 실제 폰(≤640px) : `font-size:clamp(13.5px, min(4.1vw, 2.03dvh), 19px)`
  가로는 화면 폭의 4.1%, 세로는 높이의 2.03% 를 재서 **작은 쪽**을 씁니다 — 폭은 넓은데 키가 작은 폰에서 아래가 잘리지 않습니다.
  아주 작거나(13.5px) 아주 크지(19px) 않게 막아 둡니다.
- **`px` 로 남겨 둔 것** : 테두리·그림자(1~2px 는 굵어지면 안 됨)와 `min-width`/`min-height:44px`
  (손가락 터치 최소 크기는 기기가 작아도 줄면 안 됨).
- 새로 CSS 를 쓸 때도 `px` 대신 `rem` 을 쓰세요 (16 으로 나눈 값). 안 그러면 그 부분만 기기에 따라 커지거나 작아집니다.
- 사진 상자(`#ph`)에는 **최소 높이**가 있습니다. 예전에는 `min-height:0` 이라 화면이 짧은 폰에서 높이가 0 이 되어
  **그 기기에서만 사진이 아예 안 보였습니다.**
- **브라우저 확대(두 손가락)는 막아 두었습니다**(`user-scalable=no`). 3D 화면은 두 손가락으로 돌리고 당기는데, 브라우저 확대가 같이 걸리면
  화면 전체가 커져 버튼이 밖으로 밀립니다. 대신 글자가 작으면 **쉬운 사용모드**(큰 글자)를 쓰고, 사진은 눌러서 크게 봅니다(`zoom.js`).
  자세한 이유와 검토는 [`문서/설계_배포_복구.txt`](문서/설계_배포_복구.txt) 2절.

**3D 화질** — 해상도 배율은 `overview3d.js` 의 `tunePixelRatio()` 가 그때그때 정합니다 :
건물 전체를 밖에서 보는 조감도는 가벼우므로 **2배**(또렷하게), 1인칭 실내는 무거우므로 **1.4배**(프레임 지키기).
바닥 격자는 최대로 축소(radius 260)해도 화면을 채우도록 560 으로 넓혀 두었습니다 — 예전 240 이라 뒤가 검게 보였습니다.
폰은 무거움을 줄이려고 `view3d.js` 에서 `MeshStandardMaterial` 을 `MeshPhongMaterial` 로 바꿔치기합니다 —
이 때문에 **폰에서만** 문·난간이 사라지던 사고가 있었습니다([`문서/디버깅_사례.txt`](문서/디버깅_사례.txt) 사례 1).
**폰에서만 나는 문제를 볼 때는 브라우저 폭을 좁힌 뒤 새로고침**해야 이 경로가 켜집니다 — 폭만 줄이면 안 켜집니다.

**문제 기록(설정)** — 기기에서만 나는 문제를 볼 수 있게, 설정에 「문제 기록」 줄을 뒀습니다(`pwa.js` 의 `DIAG`).
앱 판 · 오류 · 기기 · 그래픽칩 · 해상도 배율 · 폰재질 여부 · 인터넷 · 서비스 워커 · 서버(Firestore) 오류 코드가 담기고, 그 줄을 누르면 전부 복사됩니다.
평소에는 "이상 없음"만 보입니다.

**좌표 기준** — `+Z` = 엘리베이터에서 내려 −X 를 보고 섰을 때 왼쪽 복도. 층 자료의 `Top` 이 왼쪽 복도입니다
(호실 번호 순서로 추측하면 틀립니다 — `문서/발표자료_모음.txt` 20절). 3D 단위는 임의이며 실제 축척이 아닙니다.

## 왼쪽·오른쪽을 말하는 기준 (헷갈리기 쉬운 곳)

**"어느 쪽으로 도세요"는 그 사람이 지금 어느 쪽을 보고 서 있느냐에 달려 있습니다.** 앱은 세 가지를 구분합니다.

| 상황 | 보고 선 방향 | 안내 문구 |
|---|---|---|
| 2~5층 — 엘리베이터에서 **내렸다** | −X (복도 쪽) | 「내려서 왼쪽으로 도세요」 |
| **1층 — 이미 1층에 있다** | **+X (엘리베이터를 마주 봄)** | 「**엘리베이터를 마주 보고** 왼쪽으로 도세요」 |
| 1층 — 출입문 QR 로 들어왔다 | 그 문이 향한 쪽 | 「복도로 나와 왼쪽으로 도세요」 |

1층이 다른 이유 : **1층은 엘리베이터를 타고 내리는 층이 아니라 밖에서 걸어 들어오는 층**입니다.
1층에 서 있는 사람은 엘리베이터 쪽으로 걸어가 그것을 마주 보므로, 내렸을 때와 좌우가 정반대입니다
(2026-09-24 에 고침 — 그전에는 1층도 '내렸을 때' 기준이라 반대로 안내했습니다. [`문서/디버깅_사례.txt`](문서/디버깅_사례.txt) 사례 2).

**복도 사진은 도는 방향이 아니라 「목적지가 어느 복도에 있는가」로 고릅니다** (`hallCode`).
도는 방향으로 고르면 문으로 들어왔을 때 반대 복도 사진이 나옵니다.

**복도 이름**(`1층 왼쪽 복도`)은 '내렸을 때' 기준으로 붙은 이름입니다. 그래서 1층처럼 다른 자세를 기준으로
말할 때는 사진 설명에서 좌우를 빼고 `1층 복도`로만 적습니다 — 안 그러면 "오른쪽으로 도세요" 밑에
"왼쪽 복도"가 적혀 한 화면에서 엇갈려 보입니다.

검사 : `tests/check.html` 은 **내렸을 때** 기준만 잽니다(1층은 2층에서 내려온 것으로 계산).
1층에 이미 서 있는 경우는 안전망(`tests/golden.html`)이 잡습니다.

안전망은 시계를 멈추고 글꼴을 기다려 그리므로, 같은 앱이면 3D 그림까지 점 하나 다르지 않습니다.
**일부러 바꾼 화면이면** 확인한 뒤 새 기준을 기록합니다 : `pwsh -File tests\run_golden.ps1 -Mode capture -Tag v175` (지금 기준은 v174)
(그다음 `검사.ps1` · `tests/run_golden.ps1` 의 기본 `-Tag` 를 올린다). 검사마다 일부러 망가뜨린 사본으로 실패를 잡는지 확인했습니다.

5층 오른쪽 복도 29% → 37% · 47% → 46%, 4층 오른쪽 복도 38% → 61% · 53% → 71%, 창밖 22% → 35%.

**그래서 앱은 확실할 때만 말합니다** — 1·2등 장소의 유사도 차이(격차)를 확신도로 씁니다.
사진을 반으로 나눠 한쪽에서 문턱을 정하고 다른 쪽에 적용한 값입니다.

| ≥ 0.22 | 약 7% | 「아마 여기예요 : ○○」 | 자리 95.2% (재촬영 전 93.1%) |
| ≥ 0.14 | 약 22% | 「층은 ○층 같아요 — 자리는 확실하지 않아요」 | 층 96.1% (재촬영 전 0.16 에서 97.9%) |
| 그 밖 | | 「어디인지 알 수 없어요 — 번호판이 보이게 한 장 더」 | |

앱의 문턱은 자리 0.22 · 층 0.16 입니다. 반 나눠 검증이 이번에는 층 문턱을 0.14 로 골랐습니다(더 많이 답하고 96.1%).
앱 값(0.16)은 그보다 엄격한 쪽이라 그대로 두었습니다 — 새 사진으로 한 번 더 확인한 뒤 바꿉니다.
